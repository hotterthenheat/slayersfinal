### The fiber-clone method, stated so it can be challenged

React double-buffers its fiber tree. `beginWork` on a position calls
`createWorkInProgress`, which returns the *alternate* fiber object. A subtree
that bails out entirely (`childLanes === 0`) is **not** cloned — the identical
objects carry into the new current tree. So: after each commit, walk
`root.current` and record every fiber object. A position filled by a *different*
object than last commit was processed by `beginWork`.

For unmemoised **leaf** components — which is every component named in the
render tables below — that is the same thing as "the component function ran
again". It is a **lower bound on work, not an upper bound**: it cannot
distinguish an ancestor cloned only because it sits on the path to an updated
child. Container and HOC names are therefore excluded from the tables.

I first tried counting `fiber.actualDuration > 0` and it produced a plausible
but **wrong** answer (it reported Stocks re-rendering its whole table every
commit). Bailed-out fibers retain a stale `actualDuration`. That first result is
discarded; it is mentioned only so nobody re-derives it.

### 1.2 The two state systems

There are two, and only one of them is React.

**System A — React context.** Three providers, nested in `App.tsx:86-91`:
`ToastProvider → MarketDataProvider → TrackerProvider → LaunchProvider → FocusProvider`.

`MarketDataContext.tsx` is **correctly split into two contexts** and the split is
load-bearing:

- `TickerContext` (`MarketDataContext.tsx:25`) — `{ activeTicker, changeTicker }`, memoised at `:59-62`, changes only on symbol switch.
- `SnapshotContext` (`MarketDataContext.tsx:26`) — the `MarketSnapshot`, re-published every **1500 ms** by `setInterval` at `:39`.

`useTicker()` (`:72`) subscribes to the first only. `useMarketData()` (`:81`)
subscribes to **both**. `AppShell.tsx:52` correctly uses `useTicker`; `TopBar`
isolates its ticking span into a leaf component `LivePrice` (`TopBar.tsx:275-291`)
so the nav tree does not re-render. This is good work and it measurably holds —
see §4.3.

`MarketDataProvider`'s `children` element is created once in `App.tsx` and never
changes identity, so the provider re-rendering on each tick does **not** re-render
the subtree; only context consumers do. Verified by inspection of `App.tsx:83-207`
(`App` holds no state).

**System B — a module singleton.** `src/core/simulator.ts` is a 715-line IIFE
holding mutable `TICKERS` and per-symbol candle buffers, exported as a default
object (`:610-715`). `getCandles` is documented at `:620` as *"Live intraday OHLC
bars (mutated in place each tick — treat as read-only)"*. 15 of 19 route entries
reach it. Most `src/data/*` builders call `Simulator.*` **directly at call time**
rather than receiving a snapshot, which is why so many `useMemo` dependency
arrays in this codebase key on a synthetic `revision` nonce instead of on data.

**B3 — Four keys carry their schema version in the key name, which is the exact mistake this codebase documents as forbidden.**

`presets.ts:9-16` states the rule, in full:

> *The storage key is frozen at `_v1` on purpose, and the schema version rides
> INSIDE the payload. Renaming this key does not migrate a saved desk, it orphans

> their layouts gone, with nothing logged and no test red. Version the contents,
> migrate them in detach.ts, and leave the key alone.*

`slayer_pulse_workspace_v1` follows it: `WORKSPACE_VERSION = 3` lives in the
payload and `migrateWorkspace` (`detach.ts:566-596`) walks v1→v2→v3 with real

- `slayer.flowscanner.cols.v1` (`FlowScanner.tsx:17`)

- `slayer.livetape.cols.v1` (`LiveTape.tsx:33`)

`main.tsx:6-8` disables `StrictMode` for a cited RGL reason — which also means
this cannot be caught in dev. `PulseWorkspace.tsx:824-827` states the rule the
codebase already follows elsewhere: *"Kept in state + effect (not a ref mutated
during render) so it stays pure under StrictMode/concurrent rendering."*

*Smallest coherent fix:* `useEffect(() => saveToStorage(trackedSetups), [trackedSetups])`,
which is the pattern the six other persisted keys already use.

**C3 — `localStorage.setItem` runs during render, in a `useState` initializer.**

## 6. What I did **not** audit

- **Visual, typographic, a11y and palette conformance.** Out of scope for gates 2/44/38. No colour-semantics claim is made anywhere above.
- **Mobile and tablet viewports.** Every measurement is 1440×900 or 1600×1000, desktop, headless Chromium. DOM counts and frame pacing will differ.
- **`/prove-it` and `/trailer` at runtime.** Both are lazy and heavy (998 kB and 123 kB chunks). I measured their transfer cost but never drove them, so no statement is made about the three.js surface, the Monte Carlo panel, or the 78-second trailer timeline. `StateThread` and `TrailerHUD` are the two `React.memo` sites I could not verify.
- **Network throttling.** The static server is localhost. Transfer sizes are raw bytes; real-world gzip/brotli-over-3G time is not measured. The 4× CPU throttle numbers are the only "slow machine" evidence.
- **Non-headless / GPU-composited browsers.** The paint costs in A1 and A2 are from headless Chromium. The *relative* A/B (same browser, one CSS rule changed) is sound; the absolute percentages may differ on a machine with a discrete GPU.
- **Correctness of the data engines.** `src/core/quant.ts`, `simulator.ts`, `compass.ts` etc. were read only for architecture and mutation semantics. Whether the numbers they produce are right is a different gate.
- **The semantic correctness of all 25 `exhaustive-deps` suppressions.** I read every one and traced the ones on Compass, Pulse and the chart components to their consumers. For the remainder I am relying on the in-place comments plus the absence of a visible wrong number; I did not construct an adversarial input for each.
- **Whether B3's orphaning has already happened.** The four `.v1` keys have never been bumped in the history I can see, so no user data is currently orphaned. The finding is about the next bump.
- **Interaction-time performance.** Everything in §3 is an *idle* window with no user input. Drag, resize, scroll, filter and sort costs are unmeasured.
